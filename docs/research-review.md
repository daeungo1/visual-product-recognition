## 현재 상태

2026-10-27 `카메라로 대상을 인식해 AR Overlay`를 직접 요청받아 설치 없는 웹에 카메라 AR 모드를 추가했다.
폰 브라우저의 후면 카메라 영상에서 등록한 합성 패널 4종을 찾아 추적 중인 타깃 위에만 Overlay를 그린다.
네이티브 ARCore와 다른 구현이며 합성 영상과 PC 가상 카메라로만 검증했다.
실제 폰, Galaxy, 삼성 실제 제품의 결과는 없다. 설계 검토는 [웹 카메라 AR 검토](#웹-카메라-ar-검토)에 둔다.

2026-10-27 사진 요청 재검토에서는 공식 제품·지원 모델이 일치하는
AF90H19D35WN과 LS32HG802SKXKR을 선택했다.
초기 검색이 G80SD를 2026 모델로 제시했지만 해당 연식 주장은 채택하지 않았다.
에어컨 WT 번들의 지원 페이지가 WRT를 표시하는 경우도 확인해 단품 WN으로 좁혔다.
모니터는 초기800 지원 후보 대신 제품 사진·지원이 함께 확인되는802 변형으로 확정했다.
출처는 [공유 사진 참조 카탈로그](../assets/products/catalog.json)에 저장한다.

공식 사진의 공개 재배포 허가를 확인하지 못했다.
응답 불가 질문 도구의 선택 위임에 따라 원본 링크와 사용권 있는 로컬 사진 가져오기를
구현 범위로 삼았으며, 사용자가 직접 사진 재배포나 실제 모델 가이드를 승인했다고 기록하지 않는다.
이는 실물 자동 식별 또는 검수된 문제 해결 절차가 아닌 수동 사진 참조 워크플로다.
저작권 사진·임의 버튼 좌표·확인되지 않은 공식 절차를 저장소와 APK에 포함하지 않는다.

기능 검증을 비용 절감보다 우선한다. 갤럭시에 설치하는 네이티브 Android 앱을
우선 후보로 삼고, 카메라 위에 안내가 붙는 실제 동작을 검증한다.
2026-10-23 기록 기준 실제 Azure API와 연결형 APK가 구현되어 있다.
2026-10-26 익명 재확인에서 `/healthz`, `/readyz`는 200이고
인증 없는 `/v1/catalog`는 401이다. 실제품 평가 결과는 없다.
[검증 기록](./verification.md)과 [갤럭시 테스트 안내](./galaxy-test.md)에
실행한 검사와 아직 수행하지 않은 실기기 검증을 구분했다.

작업 폴더는 검토 시작 시 비어 있었다. 상위 Git 저장소는 별도 프로젝트이므로
그 저장소의 구조와 기존 파일은 변경하지 않는다.
2026-10-26 별도의 공개 저장소
[visual-product-recognition](https://github.com/daeungo1/visual-product-recognition)을 생성했다.
상위 저장소의 이력과 remote는 변경하지 않는다.

## 2026-10-26 요구사항 및 공식 자료 재검토

별도 고객 승인 PRD와 원본 고객 인터뷰는 제공되지 않았다.
직접 전달된 요구는 에어컨·세탁기·냉장고·모니터 등의 삼성 제품을 비추면
제품 이슈 해결 Overlay가 나타나는 경험이다.
고객 요구사항 대조의 근거는 이 요청, 기존 PoC 계획과 아래 리서치 항목이며,
합성 자산의 성공을 실제 고객 제품의 수용 완료로 해석하지 않는다.

구현·자동 검증·현장 검증 대기를 분리했다.

검색에서 제안한 에어컨 세부 주소는 404였고 모니터 세부 주소는 지원 홈으로
이동했다. 검증되지 않은 검색 요약을 공식 모델별 조작 절차로 등록하지 않았다.

기존 합성 리모컨의 전원·모드·온도만으로는 요청한 제품별 문제 해결 흐름을
충분히 보여주지 못했다. Android 외곽 어댑터에 네 제품형 합성 타깃 탐지,
사용자 확인, 증상 및 Overlay 안내를 추가했다.
Android와 웹은 하나의 [시나리오 카탈로그](../assets/scenarios/catalog.json)를 사용한다.
순수 Kotlin 코어의 계약과 상태 전이는 변경하지 않았다.

* 현재 FULL_TRACKING인 단일 등록 타깃만 자동 탐지 후보로 제공
* 복수·미등록·추적 불확실 상태는 비확정으로 유지하고 수동 선택을 자동 인식과 구분
* 안내 시작 후 타깃 상실·일시정지·제품 변경 시 하이라이트와 이전 증거 무효화
* 네 제품 모두 가상의 표시 상태만 확인하며 실제 고장 해소로 기록하지 않음
* 실제 삼성 제품을 게시하려면 모델별 사진·공식 절차·패널 지도·사람 검수와 현장 평가 필요

세 가지 접근을 비교했다. 문서만 수정하면 설치 불가와 계약 불일치가 남고,
전체 재설계는 검증된 코어 경계를 불필요하게 바꾼다.
따라서 기존 아키텍처를 보존하고 Android 어댑터·배포 접근성·근거 문서를 보완했다.

* API가 허용하는 500자 제목과 128단계를 Android가 거부하는 실패 테스트를 재현하고 수정
* API의 256자 한도를 넘는 페어링 코드가 Android에서 전송되는 실패 테스트를 재현하고 수정
* 코드 입력을 잘라 보내지 않고 UI에 입력 한도와 오류 상태 표시
* Git에서 제외되는 로컬 APK 링크를 공개 Release와 체크섬 링크로 변경
* PC 타깃은 GitHub Pages로 제공하고 README 첫 화면에 설치·접속·제한 배치
* 실제품 모델, 공식 절차, Galaxy 및 초심자 시험 부재는 미완료 상태 유지

## 검토 결론

공식 근거를 가진 단계 스크립트, 모델별 패널 지도, 기기 내 추적을 분리하는
접근은 적절하다. 다만 마스크 생성, 모델 식별, 화면 정합은 별개 문제다.
SAM 3가 부품 영역을 분할했다고 해서 제품 모델이 확정되거나 그 영역이
움직이는 카메라 영상에 자동으로 정합되는 것은 아니다.

비용을 더 지출하더라도 실제 제품 사진, 버튼 라벨, 모델별 가이드 검수와
현장 촬영 데이터는 생략할 수 없다. 자산이 없는 제품에 임의 좌표를 그려
실제품 지원으로 표시하지 않는다.

### 웹 카메라 AR 검토

[설치 없는 웹](https://agreeable-coast-0b8033d00.5.azurestaticapps.net/)의 카메라 AR 모드는
`getUserMedia` 영상만 분석한다. 브라우저 내장 AR API(WebXR 등)의 기기별 지원은
이번에 확인하지 못해 채택이나 배제를 판단하지 않았다.

* 정적 배포의 CSP는 같은 출처 스크립트만 허용하고 WASM 실행 권한을 주지 않는다.
  그래서 외부 라이브러리 없이 순수 JavaScript로 작성했다.
* 등록 타깃이 합성 패널 4종이므로 FAST 특징점, 방향 보정 BRIEF 기술자, RANSAC 호모그래피로
  시험할 수 있다. 학습한 AI 모델이 아니며 모션 센서도 쓰지 않는다.
* 영상 프레임은 메모리에서만 분석하고 저장하거나 전송하지 않는다.
* Overlay는 카탈로그의 정규화 영역을 현재 호모그래피로 투영한다.
  현재 추적 중이고 500 ms 이내에 관측한 선택 타깃에만 그린다. 화면 고정 좌표는 쓰지 않는다.
* 후보 확인, 제품 확인, 단계 완료는 모두 사용자가 누른다. 직접 선택은 인식 성공으로 세지 않는다.
* 영상만 쓰므로 빠른 움직임, 가림, 반사에서 Overlay가 늦거나 사라질 수 있고 이때 안내를 숨긴다.

합성 영상 측정과 구현 구조는 [README](../README.md#웹-카메라-ar-overlay)에,
실행한 검사는 [검증 기록](./verification.md)에 있다.
실제 폰 카메라, iOS Safari, 인쇄 타깃, 삼성 실제 제품은 시험하지 않았다.

## 첨부안에서 유지할 내용

* 런타임은 검수된 스크립트를 상태 머신으로 실행한다.
* 리모컨과 본체를 별도 인식 대상으로 등록하고, 서로의 호환 관계를 저장한다.
* 디스플레이 OCR은 기기에서 수행하고 VLM은 확인 지점에만 호출한다.
* 자산 생성 파이프라인과 사용자 세션 API를 분리한다.
* 식별, 정합, 단계 판정, 사용자의 완주를 별도 지표로 평가한다.

## 반드시 보완할 내용

### 제품 모델과 리모컨 모델을 구분

한 리모컨이 여러 본체 모델에 사용될 수 있다. 비슷한 외관의 본체도 존재하므로
외관 임베딩 점수만으로 정확한 모델을 확정하지 않는다.
본체의 모델 라벨 OCR, 등록한 제품 정보, 후보 확인을 결합한다.
지원하지 않는 제품과 저신뢰 결과는 명시적으로 식별 불가로 반환한다.

자동 식별 결과, 후보에서 사용자가 선택한 결과, 사용자가 모델명을 직접
입력한 결과를 구분해 기록한다. 수동 선택을 자동 식별 성공으로 집계하지 않는다.

### ARCore 추적 상태를 정확히 처리

Google 문서에 따르면 Augmented Images는 움직이는 평면 이미지도 추적한다.
따라서 움직이는 리모컨에 사용할 수 없다고 단정할 이유는 없다.
그러나 가림이나 시야 이탈 이후에는 마지막 자세를 유지할 수 있다.
이때 움직인 리모컨 위에 올바른 안내가 붙는다고 보장할 수 없다.

움직이는 대상의 버튼 안내는 `TrackingState.TRACKING`과
`TrackingMethod.FULL_TRACKING`을 모두 만족할 때만 표시한다.
`LAST_KNOWN_POSE`, `PAUSED`, `STOPPED`에서는 대상 하이라이트를 숨기고
재탐지를 안내한다. 전역 고정 앵커로 움직이는 리모컨을 대신 추적하지 않는다.

초기 탐지에는 기준 이미지의 평면성, 특징점, 충분한 화면 점유율이 필요하다.
Google은 초기 탐지 시 이미지가 카메라 프레임의 최소 25%를 차지하도록
안내한다. 기준 이미지 품질은 `arcoreimg`로 점검한다.
흰색 무늬 없는 패널, 반사 디스플레이, 반복 버튼은 별도 실측이 필요하다.

단일 평면의 지도는 열린 덮개, 분리된 필터, 곡면 전체를 동시에 설명하지 못한다.
서로 움직이는 강체와 열린 상태, 닫힌 상태의 자산을 분리한다.

### 카메라 소유권을 단일화

CameraX와 ARCore가 각각 독립적으로 카메라를 여는 구조를 기본값으로 쓰지 않는다.
AR 화면에서는 ARCore 세션을 프레임 공급자로 삼아 CPU 이미지를 OCR에 전달하는
방식을 우선 검토한다. 일반 촬영 화면에 CameraX를 사용한다면 전환 시 세션을
종료하거나 일시정지한다.

동시 카메라 공유가 실제로 필요할 때만 Google의 Shared Camera와 Camera2 경로를
검토한다. OCR 작업은 제한된 빈도로 처리하고 사용한 이미지 버퍼를 해제한다.

### TV 화면과 리모컨 사이의 시점 전환 지원

한 손의 휴대폰 카메라에 리모컨 버튼과 TV 메뉴가 항상 함께 들어오지 않는다.
각 단계에 현재 관찰할 대상과 확인할 대상을 구분한다.
리모컨 촬영에서 TV 화면 촬영으로 전환하면 이전 리모컨 하이라이트를 숨긴다.
다시 리모컨을 비추면 재탐지한다. 두 대상을 하나의 고정된 좌표계로 취급하지 않는다.

### OCR과 VLM 결과를 단계 전환과 분리

한글과 영문을 읽을 수 있는 ML Kit 한국어 인식기를 검토한다.
최초 실행 시 모델 다운로드에 의존하지 않도록 번들 모델을 우선 후보로 삼는다.
화면 전체의 우연한 문자열이 아닌 현재 단계의 디스플레이 ROI를 판정한다.

자동 전환에는 안정된 복수 관측, 현재 단계 ID, 요청 ID, 증거 시각을 사용한다.
지연된 응답이나 중복 요청이 다른 단계를 완료시키지 않도록 한다.
VLM 결과는 `pass`, `fail`, `unsure`로 구분하고 `unsure`를 성공으로 처리하지 않는다.
사용자 확인과 자동 확인은 평가 데이터에서도 구분한다.

모든 공식 가이드는 출처, 적용 모델, 버전, 검수 상태를 가진다.
미검수 스크립트는 실제품 모드에서 실행하지 않는다.
LLM이 만든 단계나 버튼 좌표를 검수 없이 실행하지 않는다.
안전과 관련된 장착 상태는 VLM의 사진 판정만으로 보증하지 않는다.
앱은 가전에 제어 명령을 보내지 않는다.

### 코어 경계는 생성 후 보호

처음부터 빈 코어를 수정 금지로 만들면 도메인과 포트를 구현할 수 없다.
먼저 순수 Kotlin의 도메인, 상태 머신, 포트와 계약 테스트를 만들고 승인한다.
이후 Android, ARCore, ML Kit, HTTP, Azure 구현을 어댑터로 제한한다.
코어의 변경이 필요하면 계약 변경과 회귀 테스트를 동반한다.
Python 서버가 Kotlin 코어를 직접 재사용한다고 가정하지 않고,
공통 JSON Schema와 계약 테스트로 경계를 검증한다.

## Azure 구성 후보

아래는 역할별 후보이며, 구독과 지역이 확정된 배포 계획은 아니다.
비용 때문에 상시 가동을 배제하지 않으며, 사용자 테스트 중에는 콜드 스타트를
피하도록 API와 식별 모델을 예열하는 구성을 우선한다.

| 역할 | 후보 서비스 | 구현 원칙 |
|------|-------------|-----------|
| 가이드, 식별, 판정, 세션 API | Container Apps, FastAPI | HTTPS, 인증, 준비 상태 확인, 테스트 중 최소 인스턴스 유지 |
| 이미지 식별 | 이미지 임베딩 모델과 AI Search | 카테고리 및 대상 종류 필터, 동일 임베딩 버전, Top-k와 식별 불가 |
| 확인 지점 VLM | Foundry의 이미지 입력 및 구조화 출력 모델 | 실제 구독의 모델 버전과 쿼터 확인 후 고정 |
| 오프라인 가이드 작성 | Content Understanding과 Foundry | 원문 근거 및 사람 검수 후 게시 |
| 오프라인 마스크 | GPU 작업의 SAM 3 | 가중치 접근 권한, 라이선스, CUDA와 메모리 사전 검증 |
| 자산 | 비공개 Blob Storage | 읽기 권한 제한, 원본 및 검수본 버전 구분 |
| 세션과 평가 이벤트 | Cosmos DB | 세션별 순서, 중복 방지, 보존 기간 적용 |
| 컨테이너 이미지 | Azure Container Registry | 관리 ID로 접근 |
| 인증과 비밀 | Microsoft Entra ID, Managed Identity, 필요 시 Key Vault | APK에 Azure 키나 클라이언트 비밀을 포함하지 않음 |
| 관측 | Application Insights와 Log Analytics | 단계 지연, 실패 원인, 추적 상실 기록. 원본 프레임을 로그에 넣지 않음 |

API Management, Web PubSub, Agent Service와 Voice Live는 필수로 묶지 않는다.
가이드 선택과 단계 실행에 에이전트 오케스트레이션이 반드시 필요한 것은 아니다.
초기 음성 낭독에는 Android TTS를 검토한다.
추가 서비스는 원격 상담, 여러 화면 동기화, 대화형 지원이라는 실제 요구에 연결한다.

Azure GPU는 모든 지역에 제공되지 않는다. 2026-10-21 확인한 문서에서
Japan East는 T4를 지원하지만 A100은 지원하지 않으며,
Korea Central은 서버리스 GPU 지원 지역 표에 없다.
SAM 3와 식별 모델의 지역, GPU 메모리 요구와 쿼터를 각각 검증한다.
서버리스 GPU를 쓰려면 workload profiles 환경이 필요하다.
지역 간 사진 이동이 필요한 구성은 배포 전에 명시한다.

## 제안하는 검증 순서

1. 제품과 리모컨의 모델 ID, 호환 관계, 공식 가이드, 촬영 및 데이터 사용 권한을 확보한다.
2. 정확한 제품이 없어도 실행 가능한 별도 데모 타깃과 시뮬레이션 스크립트를 만든다.
3. 갤럭시에 APK를 설치해 카메라 권한, 추적, 한글 OCR, 음성 낭독, 수동 진행을 확인한다.
4. Azure API, 영속 세션, 이미지 식별, 구조화 VLM 판정을 실제로 연결한다.
5. 검수된 실제품 자산을 등록하고 에어컨 모드 및 온도 설정부터 평가한다.
6. TV 메뉴와 리모컨 시점 전환을 평가한다.
7. 필터 관련 시나리오와 선택 사항인 에어드레서는 공식 모델별 절차 및 안전 검수 후 추가한다.

단계 2의 결과를 실제품 성능으로 집계하지 않는다.
실제품 없이 모든 가전에 대한 식별 및 정합을 검증했다고 보고하지 않는다.

## 제안하는 수용 기준

아래 수치는 설계 논의용 목표이며 실측 결과가 아니다.
가장 먼저 확보한 실제 제품과 갤럭시 기기에서 타당성을 확인한 뒤 고정한다.

| 항목 | 제안 기준 | 측정 방법 |
|------|-----------|-----------|
| 자동 모델 식별 | 등록 모델 Top-1 90% 이상, Top-3 98% 이상 | 등록용 촬영과 다른 세션의 정답 모델 라벨 사용. 수동 선택 제외 |
| 미지원 제품 처리 | 자동 확정 오탐 5% 이하 | 미지원 제품과 유사 리모컨을 별도 음성 집합으로 평가 |
| 버튼 정합 | 투영 중심 오차 p95가 버튼 짧은 변의 25% 이하 | 프레임별 정답 버튼 영역과 비교. 추적 실패 프레임도 별도 집계 |
| 유효 안내 가용률 | 지정 촬영 조건의 90% 이상 | 정확한 하이라이트가 표시된 시간 / 전체 대상 관찰 시간 |
| 추적 상실 처리 | 유효 추적 상실 후 다음 렌더 프레임에 대상 안내 제거 | 손 가림, 시야 이탈, 대상 전환 테스트 |
| 추적 성능 | 추적 및 오버레이 처리 p95 33ms 이하 목표 | 지정 갤럭시에서 프레임 타이밍 및 발열과 함께 측정 |
| OCR 자동 진행 | 잘못된 단계 자동 전환 1% 이하 | 메뉴, 배경 문구, 반사, 흐린 영상과 중복 관측을 포함 |
| VLM 확인 | 자동 완료 정밀도 95% 이상 목표 | 독립 라벨 기준 precision, recall, unsure 비율을 함께 보고 |
| 서버 응답 | 식별 p95 3초, VLM p95 5초 이내 목표 | 예열 및 콜드 스타트, 단말 네트워크 왕복 시간을 구분 |
| 사용자 완주 | 초심자 5명 중 4명 이상이 상담원 도움 없이 완료 | 수동 확인 횟수, 실패 단계, 소요 시간과 함께 보고 |

5명 시험은 정성적 PoC이며 통계적 일반화를 하지 않는다.
자동 확인의 분모와 사용자 확인의 분모를 섞지 않는다.
식별과 정합이 실패한 시도도 전체 시도 수에서 제외하지 않는다.

## 최초 배포 조사 당시의 전제조건

다음은 2026-10-21 당시 조사 이력이다. 현재 미배포 상태라는 의미가 아니다.
후속 배포와 검증은 [Azure 구성](./azure-architecture.md) 및
[검증 기록](./verification.md)을 따른다.

* Azure CLI의 초기 구독 조회와 사용자 조회가 15초 안에 응답하지 않았다.
  이후 직접 조회에서 약 55초의 CLI 기동 시간을 확인했다.
  긴 제한 시간으로 기본 구독의 ARM 접근과 사용자 조회가 성공했다.
* Foundry MCP는 자격 증명 오류를, 구독 목록 MCP는 타임아웃을 반환했다.
* VS Code Azure 확장에는 로그인되어 있으나 선택된 구독이 없었다.
* 확장의 로그인 상태만으로 CLI 및 ARM 배포 인증이 성공했다고 판단하지 않는다.
* 확인된 CLI 기본 구독은 `ME-MngEnvMCAP359144-daeungo-1`
  (`2cf925b6-80cb-4567-abda-5ccd3010aab5`)이며 상태는 `Enabled`다.
* CLI와 VS Code 확장의 테넌트가 다르다. 이후 배포와 검증은 확인한 CLI 구독을
  명시하며, 아직 리소스를 만들거나 구독 설정을 변경하지 않았다.
* 초기 기본 경로에 Android SDK와 ADB가 없었고 PATH의 Java는 JDK 11이었다.
  이후 프로젝트 전용 `.tools`에 JDK 17, Android SDK 35와 Gradle 8.11.1을 준비해 빌드했다.
  시스템 기본 Java 설정은 변경하지 않았다.
* 별도 ADB 포트로 실제 연결을 확인했지만 연결된 기기가 없었다.
* 실제품 모델명, 본체 및 리모컨 사진, 실제 테스트 갤럭시의 모델과 OS는 제공되지 않았다.

확인된 CLI 기본 구독에서 모델 카탈로그와 일부 쿼터를 조회했다.
서버리스 GPU의 환경별 할당과 전체 구성의 가용성은 아직 확인하지 못했다.
구체적인 조회 범위와 가격은 [Azure 아키텍처](./azure-architecture.md)에 기록했다.
구성 생성 승인과 리소스 배포 승인은 별도로 받는다.
비용 사용 허용은 잘못된 구독 선택이나 검증되지 않은 성능 주장에 대한 승인이 아니다.
